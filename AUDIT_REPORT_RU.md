## 4. Подтверждённые ошибки (по серьёзности)

### 4.1 КРИТИЧЕСКАЯ: несоответствие правилам ADX в режиме рынка

- Файлы:
  - `BOOK_RULES.md:19-23`
  - `src/engine/BelyaevPipeline.cpp:28-55`
- Описание:
  - В правилах книги указано:
    - `ADX[c] < ADX[c-1]` → `FLAT (CCI + DM)`
    - `ADX[c] > ADX[c-1]` → `TREND (EMA + MACD)`
    - `ADX[c] == ADX[c-1]` → `50/50 (неопределенность)`
    - `ADX[c] < 20` → `50/50 (неопределенность)`
  - В коде реализовано так:
    - `bool is_flat = (f.adx[idx] < f.adx[idx - 1]);`
    - если `f.adx[idx] < 20.0` → неопределённость;
    - иначе выполняется `else` и считается TREND, даже при `ADX == prevADX`.
  - Это прямое расхождение с формальной логикой книги.
- Почему это важно:
  - Система может принимать торговое решение в условиях неопределённости, где книга требует 50/50.
  - Это влияет на режим рынка и последующую агрегацию индикаторов.
- Рекомендуемое исправление:
  - Использовать явную цепочку условий:
    - if ADX < 20 => 50/50
    - else if ADX == prevADX => 50/50
    - else if ADX < prevADX => FLAT
    - else => TREND

### 4.2 КРИТИЧЕСКАЯ: линейный поиск фракталов/дивергенции потенциально использует look-ahead

- Файлы:
  - `BOOK_RULES.md` (правила о “поиске без заглядывания в будущее” в сопоставлении с аудиторским реестром)
  - `AUDIT_REGISTRY.md:21-23`
  - `src/rules/DivergenceFinder.cpp:24-43`
- Описание:
  - В коде при проверке фракталов используется цикл вида:
    - `for (size_t k = 1; k <= fk; ++k) { ... if (bars[i].high <= bars[i + k].high) ... }`
    - Аналогично для `i - k` и `i + k`.
  - Это означает, что при анализе текущей точки `i` используется “будущее” (`i + k`) в том же вычислительном пассе.
  - Для реального торгового расчёта это недопустимо, если сигнал должен быть вычислим только на исторических данных без знания будущего.
- Почему это важно:
  - Сигнал дивергенции может формироваться на основе данных, которых не было на момент расчёта.
  - Это не просто теоретическая оговорка — это реальная логика, которая искажает сигналы.
- Рекомендуемое исправление:
  - Исключить проверку по будущим значениям при определении текущего экстремума.
  - Использовать только исторически известные значения в момент времени `i`.

### 4.3 КРИТИЧЕСКАЯ: фигуры не реализованы в полном объёме и не соответствуют правилам приоритетов

- Файлы:
  - `BOOK_RULES.md:46-105`
  - `src/rules/FigureDetector.cpp:27-69`
- Описание:
  - Книга задаёт 44 фигуры с чёткими номерами и приоритетами:
    - 1–10
    - 11–24
    - 25–44
    - 45–46 дополнение
  - В коде фактически присутствуют только несколько фрагментарных условий, без:
    - явного соответствия каждому номеру фигуры;
    - фиксированной логики выбора по приоритету;
    - полного покрытия 44 фигур;
    - разделения на “специфичную фигуру” и “дополнение”.
  - Это не соответствует формальному описанию главной части книги.
- Почему это важно:
  - Логика “почти как книга” в таком виде может давать ложные или неполные сигналы.
  - Это критично для торговой модели, основанной на фигурах.
- Рекомендуемое исправление:
  - Реализовать фигуры как отдельные правила с номером, а затем выбирать результат по приоритету: более специфичная фигура / больший номер / дополнение 45–46 как дополнение, а не замена.

### 4.4 ВЫСОКАЯ: несогласованное/неполное применение “тяжёлого графика”

- Файлы:
  - `BOOK_RULES.md:9-10`
  - `BOOK_RULES.md:17-18`
  - `src/rules/RunAnalyzer.cpp:29-33`
  - `src/rules/ScoreCalculator.cpp:78-81`
- Описание:
  - В книге “тяжёлый график” — следующий старший ТФ (D→W, W→M).
  - В коде логика “тяжёлого графика” реализована асимметрично и неполно:
    - в `RunAnalyzer` проверяется только одна ветка (`heavy_chart_trend == 1 && direction == Down`);
    - в `ScoreCalculator` есть ещё одна проверка, но она также не симметрична и не покрывает равновесный/контрастный сценарий полностью.
  - По сути, есть частичная проверка, но отсутствует полноформатная формализация всех случаев.
- Почему это важно:
  - Тяжёлый график должен ограничивать или усиливать локальный сигнал. Если логика неполная, система может нарушать правило “старший таймфрейм важнее локального”.
- Рекомендуемое исправление:
  - Описать и реализовать обе симметричные ветки:
    - старший вверх блокирует/ослабляет локальный вниз;
    - старший вниз блокирует/ослабляет локальный вверх;
    - обе ветки должны быть явно и одинаково применены.

## 5. Предположения / потенциальные риски, требующие отдельной верификации

### 5.1 Неясная логика слияния эталонов в `ScoreCalculator::merge`

- Файл: `src/rules/ScoreCalculator.cpp:85-102`
- Описание:
  - Код устанавливает:
    - `res.reference_direction = (a.reference_direction == b.reference_direction) ? a.reference_direction : 0;`
  - Это означает, что если эталоны не совпадают, результат “сбрасывает” направление, хотя в правилах может быть ожидаем конфликт/неопределённость или особое поведение.
- Статус:
  - Не подтверждён как явная ошибка, но это зона повышенного риска.
- Рекомендуемое исправление:
  - Чётко формализовать поведение при несовпадении эталонов, а не скрывать это через ноль.

### 5.2 Слабая формализация “конфликтов” между индикаторами и вероятностями

- Файлы:
  - `BOOK_RULES.md:24-29`
  - `BOOK_RULES.md:193-208`
  - `src/engine/BelyaevPipeline.cpp:37-55`
- Описание:
  - Книга имеет строгие правила слияния вероятностей и конфликтов `50/50`.
  - В коде агрегация проходит через `merge()` и `apply_reference_rule()`, но правила слияния и конфликтных состояний не всегда очевидно соответствуют книге.
- Статус:
  - Похоже на структурную уязвимость модели, но требует отдельного тестового матричного анализа.
