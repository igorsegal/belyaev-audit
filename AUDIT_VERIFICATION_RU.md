## Методология и ограничения

- Проверялись только фактические формулировки в `BOOK_RULES.md` и реализация в `src/`.

## 1) ADX equality case: статус CONFIRMED

### Что утверждал предыдущий аудит

- В `src/engine/BelyaevPipeline.cpp` ADX equality case is handled as TREND, while `BOOK_RULES.md` says `ADX[c] == ADX[c-1]` -> `50/50`.

### Фактическое правило в книге

`BOOK_RULES.md:19-23`:
- `ADX[c] < ADX[c-1]` И `ADX[c] >= 20` → `FLAT (CCI + DM)`.
- `ADX[c] > ADX[c-1]` И `ADX[c] >= 20` → `TREND (EMA + MACD)`.
- `ADX[c] == ADX[c-1]` → `50/50 (неопределенность)`.
- `ADX[c] < 20` → `50/50 (неопределенность)`.

### Фактическая реализация в C++

`src/engine/BelyaevPipeline.cpp:28-55`:

```cpp
bool is_flat = (f.adx[idx] < f.adx[idx - 1]);
if (f.adx[idx] < 20.0) {
    node.mode = "ADX < 20 (неопределенность)";
    node.body_forecast.up_probability = 50.0;
    node.body_forecast.down_probability = 50.0;
    node.body_forecast.is_conflict = true;
    node.is_uncertain = true;
    return node;
}
...
else {
    node.mode = "TREND (MACD+EMA)";
    ...
}
```

### Почему это подтверждено

Если `f.adx[idx] == f.adx[idx - 1]` и оба значения `>= 20`, тогда:
- `is_flat == false`;
- `f.adx[idx] < 20.0` -> `false`;
- код попадает в `else` и выбирает `TREND`.

Это напрямую противоречит правилу книги: при равенстве ADX требуется `50/50`.

### Минимальный воспроизводимый тест

Вход:
- `prevADX = 30.0`
- `currADX = 30.0`
- `currADX >= 20`

Ожидание по правилам:
- `50/50 (неопределенность)`

Фактический результат кода:
- `TREND (MACD+EMA)`

Это полностью воспроизводимый тест по прямой ветвистой логике.

## 2) DivergenceFinder: статус NOT_PROVEN для термина “look-ahead”, но подтверждён факт будущих соседей при подтверждении фрактала

### Что утверждал предыдущий аудит

- `DivergenceFinder.cpp` использует look-ahead.
- Оно “проверяет будущие свечи и поэтому обязательно нарушает торговые правила”.

### Фактическая формулировка книги и API

`include/rules/DivergenceFinder.h:13-20`:
- `fractal_k` — “сколько баров слева/справа для подтверждения фрактала (обычно 2)”

То есть в намерении API явно заложен “слева/справа” для фрактала.

### Фактическая реализация

`src/rules/DivergenceFinder.cpp:24-43`:

```cpp
for (size_t i = start; i <= last_visible; ++i) {
    bool is_high = true, is_low = true;
    for (size_t k = 1; k <= fk; ++k) {
        if (bars[i].high <= bars[i - k].high || bars[i].high <= bars[i + k].high) is_high = false;
        if (bars[i].low  >= bars[i - k].low  || bars[i].low  >= bars[i + k].low)  is_low  = false;
    }
    if (is_high) price_highs.push_back(i);
    if (is_low)  price_lows.push_back(i);
}
```

### Что именно подтверждено

Подтверждён следующий факт:
- Фрактал определяется с проверкой соседей как слева, так и справа.
- Для `fk = 2`, фрактал бару `i` подтверждается только после того, как есть доступ к `i+1` и `i+2`.

Это подтверждается и кодом, и комментариями API.

### Важное различие: look-ahead vs delayed confirmation

Для доказательства “look-ahead” нужно показать, что сигнал для текущего момента используется до того, как соответствующие будущие свечи стали доступными в торговом алгоритме.
Фактический код этого не доказывает.

То, что код показывает, — это:
- фрактал формируется как событие, подтверждаемое после появления соседей справа;
- поэтому сигнал становится доступным только после задержки по времени, а не в текущем моменте.

### Когда именно фрактал подтверждается

При `fk = 2`:
- бар `i` не считается фракталом, пока внешний цикл не дойдёт до `i` с доступными соседями `i ± 1`, `i ± 2`.
- Поэтому в реальном потоке сигнал становится подтверждённым не раньше, чем после появления нужного числа следующих свечей.

### Когда сигнал становится доступен торговому алгоритму

Сигнал становится доступен после того, как функция `find()` уже рассчитала фракталы для всей рассматриваемой истории. В этом случае алгоритм работает на уже сформированной выборке, а не на предпоследней свече.

Использовать слово “look-ahead” как прямое обвинение без доказательства, что торговый сигнал был использован до получения этих данных, нельзя.

### Вывод по статусу

- Факт подтверждён: фрактал проверяется на соседях с обеих сторон.
- Утверждение “сигнал генерируется с использованием ещё не существовавших данных для текущего решения” — `NOT_PROVEN`.

### Минимальный воспроизводимый тест

Вход:
- `fk = 2`
- значения/баров достаточно, чтобы `i` проверяется с `i−2`, `i−1`, `i+1`, `i+2`

Результат по коду:
- `is_high` и `is_low` зависят от `bars[i + k]` при `k = 1,2`.

Это показывает, что подтверждение фрактала зависит от будущих соседей, но не доказывает, что торговый алгоритм использовал этот сигнал раньше времени.

## 3) FigureDetector completeness: статус CONFIRMED

### Что утверждал предыдущий аудит

- `FigureDetector.cpp` не реализует полный набор 44 фигур Беляева и приоритетов книги.

### Фактическое правило в книге

`BOOK_RULES.md:46-105` задаёт 44 фигуры и их приоритеты:
- 1–10, 11–24, 25–44, 45–46
- приоритеты: `11–12 > 9–10`, `41–44 > 37–40`

### Фактическая реализация

`src/rules/FigureDetector.cpp:27-69` содержит набор условных проверок, но не действует как таблица фигур по номерам. Нет ветвей вида “rule 21 / 22 / 41 / 44”, нет явного выбора “специфичная фигура” по номеру.

### Почему это подтверждено

- В коде нет отдельной логики на номера фигур `1..44`.
- Книга описывает 44 фигуры, а код возвращает только `int score` без привязки к конкретному идентификатору фигуры.
- В коде нет явного оператора выбора фигуры с наибольшим номером, как это описано в правилах.

### Минимальный воспроизводимый тест

Проверка невозможна как прямое соответствие “правило №N (= X) vs реализация” без доработки кода, потому что код не хранит номер фигуры и не возвращает набор “подошла фигура №N”.

Тем не менее факт подтверждён по коду и тексту правил: логика не соответствует “44 фигур” как формальному списку.

### Статус

`CONFIRMED` — по факту отсутствует полноформатная реализация 44 фигур.

## 4) Heavy trend logic: статус CONFIRMED с оговоркой

### Что утверждал предыдущий аудит

- heavy trend logic is asymmetric or incomplete.

### Фактическое правило в книге

`BOOK_RULES.md:9-10`:
- “Тяжёлый график — следующий старший ТФ (D→W, W→M).”

### Фактическая реализация в `RunAnalyzer`

`src/rules/RunAnalyzer.cpp:29-33`:

```cpp
if (heavy_chart_trend != 0) {
    if (heavy_chart_trend == 1 && res.direction == RunDirection::Down) {
        res.reason += " | Прогон против тяжелого графика";
    }
}
```

### Что подтверждено

- Для `heavy_chart_trend == 1` и `direction == Down` есть отдельный блок.
- Для `heavy_chart_trend == -1` и `direction == Up` такого блока нет.
- Значит логика в `RunAnalyzer` асимметрична по формулировке причины.

### Что не подтверждено

В `ScoreCalculator::calculate` есть симметричная проверка:

`src/rules/ScoreCalculator.cpp:78-81`:

```cpp
bool against_heavy = (ref_direction > 0 && heavy_chart_trend < 0) || (ref_direction < 0 && heavy_chart_trend > 0);
if (against_heavy) { if (ref_direction > 0) score -= 25; else score += 25; }
```

Это уже симметрично. Поэтому общий вывод “весь heavy trend logic asymmetrical” — неверен, но частичный вывод о `RunAnalyzer` — подтверждён.

### Минимальный воспроизводимый тест

Вход A:
- `heavy_chart_trend = 1` (up)
- тренд `ref_direction = -1` (down)
- ожидается “против тяжелого графика” в `RunAnalyzer`

Фактический результат:
- строка причины добавляется, потому что ветка `heavy_chart_trend == 1 && direction == Down` срабатывает.

Вход B:
- `heavy_chart_trend = -1` (down)
- `ref_direction = 1` (up)
- `RunAnalyzer` не добавляет такую строку.

Это доказывает асимметрию именно в `RunAnalyzer`, а не во всём пайплайне.

### Статус

`CONFIRMED` для частного утверждения: `RunAnalyzer` асимметричен по причине. 
`REFUTED` для более широкого утверждения “весь heavy trend logic asymmetrical/incomplete” в отношении `ScoreCalculator`.

## 5) `ScoreCalculator::merge`: статус NOT_PROVEN

### Что утверждал предыдущий аудит

- В `merge()` эталон сбрасывается на `0` при несовпадении сигналов, что нарушает книгу.

### Фактическое правило в книге

`BOOK_RULES.md:12-18` задаёт правило эталона и правило `sign(S)`.

`BOOK_RULES.md:24-29` задаёт слияние вероятностей, но не задаёт точный “merge reference_direction” для двух индикаторов в виде кода.

### Фактическая реализация

`src/rules/ScoreCalculator.cpp:85-102`:

```cpp
res.reference_direction = (a.reference_direction == b.reference_direction) ? a.reference_direction : 0;
```

### Что можно сказать строго по фактам

- В книге нет явной формулы, которая бы явно определяла, что делать с `reference_direction` при несовпадении двух индикаторов.
- В коде это поведение явно существует, но оно не имеет прямого опровержения в книге.
- Поэтому нельзя утверждать, что это “нарушение правил” без дополнительной спецификации или тестов на реальном наборе условий.

### Минимальный воспроизводимый тест

Тест возможен формально:
- `a.reference_direction = 1`
- `b.reference_direction = -1`
- вызвать `merge(a, b)`
- результат: `reference_direction == 0`

Но это лишь показывает поведение кода, а не противоречие книге, потому что в книге такого сценария напрямую не описано.

### Статус

`NOT_PROVEN`.

## 6) Конфликтные состояния и pipeline: статус NOT_PROVEN

### Что утверждал предыдущий аудит

- `pipeline conflict logic` is structurally broken.

### Фактическая формулировка книги

`BOOK_RULES.md:24-29`:
- “Конфликт: если `P_up == 50` И `P_down == 50` → **не торгуем**.”

`BOOK_RULES.md:17-18`:
- `S == 0` → `50/50`.

### Фактическая реализация

`src/rules/ScoreCalculator.cpp:15-47` implements reference rule and sets conflict for raw sum 0 and for 50/50 probabilities.

`src/engine/BelyaevPipeline.cpp:56-62`:

```cpp
if (result.is_conflict) {
    node.is_uncertain = true;
} else {
    node.is_uncertain = false;
    node.trend_direction = (result.up_probability > 50.0) ? 1 : -1;
}
```

### Что подтверждено

- В коде есть явная проверка `result.is_conflict` и установка `node.is_uncertain = true`.
- Это соответствует общей идее книги: конфликт -> не торгуем.

### Что не подтверждено

- Нет доказательства, что это “структурно сломано”.
- Для утверждения “сломано” нужны формальные контрпримеры на реальных входах, которых в предыдущем аудите не приведено.

### Минимальный воспроизводимый тест

Вход:
- `ForecastResult` с `up_probability=50`, `down_probability=50`, `is_conflict=true`

Ожидание по книге:
- “не торгуем”

Фактический результат:
- pipeline marks `node.is_uncertain = true`

Это делает код логически согласованным с правилами конфликтов, а не сломанным.

### Статус

`NOT_PROVEN`.

- для `DivergenceFinder` нужно различать “фрактал подтверждается на соседях справа” и “сигнал использован до появления данных”; эти вещи не эквивалентны.
